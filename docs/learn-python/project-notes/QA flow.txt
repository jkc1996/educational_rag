=====================================================================
ASK QUESTION (QA) PIPELINE – RAG GENERATION FLOW
Chapter 5 – Question Answering & Generation Layer
=====================================================================

PURPOSE
-------
This pipeline handles runtime question answering using a
Retrieval-Augmented Generation (RAG) architecture.

Goal:
- Retrieve the most relevant document chunks from ChromaDB
- Augment the LLM prompt with retrieved context
- Generate a grounded, explainable answer
- Optionally return supporting context for transparency
- Support multiple LLM backends
- Enable feedback-driven improvement

This is the GENERATION side of RAG.


=====================================================================
HIGH-LEVEL RAG FLOW
=====================================================================

User Question
     ↓
Subject-based Vector DB selection
     ↓
RAG Chain (cached or newly built)
     ↓
Semantic Retrieval (Top-k chunks)
     ↓
(Optional) Feedback-aware re-ranking
     ↓
Context formatting
     ↓
Prompt + LLM
     ↓
Answer generation
     ↓
Return answer + sources (+ optional context)

Output:

-------------------------------------------------
1.2 RAG Chain Cache (Performance Optimization)
-------------------------------------------------

Cache key:
(chroma_dir, llm_choice)

Why cache:
- Vectorstore loading + LLM initialization are expensive
- These components do NOT change per question
- Reusing them improves latency significantly

Flow:
IF cache hit:
    reuse RAG chain
ELSE:
    build new RAG chain
    store in cache

This reflects production-grade GenAI system design.


caching requirement in bit deep:

1️⃣ What exactly is being cached?
cache_key = (chroma_dir, llm_choice)
rag_chain_cache[cache_key] = rag_chain

2️⃣ What is inside "rag_chain" (important)

rag_chain is NOT just an LLM.

It contains:

Loaded embedding model

Loaded Chroma vectorstore

Configured retriever

Optional feedback-aware reranker

Loaded LLM client (Groq / Gemini / Ollama / OpenAI)

Prompt + formatting logic

Creating this repeatedly is expensive.

3️⃣ Why cache by Chroma directory?
chroma_dir = f"outputs/chroma_{subject.replace(' ', '_').lower()}"

Meaning:

Each subject → its own vectorstore

Each vectorstore → separate knowledge base

So:

ML subject ≠ NLP subject

PDF set A ≠ PDF set B

If you reused the same retriever accidentally:
❌ Wrong answers
❌ Cross-subject contamination

4️⃣ Why cache by LLM choice?

Because LLMs are part of the chain.

Example:

Groq = fast, lower latency

Gemini = better reasoning, rate-limited

Ollama = local, slower, offline

Each LLM:

Has different clients

Different token limits

Different latency

Different behavior

So:

Same PDFs + different LLM = different RAG chain


If you didn’t separate by llm_choice:
❌ Gemini chain could answer a Groq request
❌ Wrong cost / latency assumptions

5️⃣ Why caching is necessary (real reasons)
🔹 Reason 1: Performance

Without cache:

Every question →
  load embedding model
  load Chroma DB
  create retriever
  create LLM client
  build chain


That’s slow and wasteful.

With cache:

First question → build once
Next questions → reuse instantly

- No re-embedding

Output:

-------------------------------------------------
2.3 Retriever creation (retriever.py)
-------------------------------------------------

Function:
get_retriever(vectorstore, k=5)

Purpose:
- Convert vectorstore into a retriever interface
- Performs semantic similarity search

Input:
- User question (string)

Output:
List[Document] (LangChain Documents)

Each Document contains:
- page_content (chunk text)
- metadata:
    - source_pdf
    - page number
    - chunk_uid


-------------------------------------------------
2.4 Feedback-Aware Retriever (Optional)
-------------------------------------------------

Component:
FeedbackAwareRetriever

Purpose:
- Improve ranking using user feedback
- Does NOT change retrieval candidates
- Only reorders top-k results

Feedback logic:
score = upvotes - downvotes
penalty = -score * beta

Sorting:
- Lower penalty = higher priority
- Stable ordering preserved if no feedback exists

Why important:
- Enables human-in-the-loop RAG
- Supports continual system improvement
- Aligns with evaluation & feedback loop in report

-------------------------------------------------
4.4 Parallel execution (Critical design choice)
-------------------------------------------------

RunnablePassthrough():

in code we see this: "question": RunnablePassthrough()

Means:

Take the original user question

Pass it unchanged into the prompt

Why this matters:
- Enables explainability
- Allows citation and context preview
- Supports evaluation and feedback

1️⃣ What do we mean by “parallel execution” here?

Parallel execution means:

From the same user question, two independent computations are triggered at the same time, and their results are combined.

In your QA pipeline, those two computations are:

Retrieve documents (sources)

Generate an answer using those documents

2️⃣ Where exactly does this happen in YOUR code?

This line 👇 is the key:

combined = RunnableParallel(
    sources=retriever,   # raw Document[] for citations
    answer=answer_chain
)


This is not just syntax sugar.
This is a LangChain execution graph.

3️⃣ What happens internally when you call:
result = rag_chain.invoke(question)


LangChain executes this graph:

                 question
                     |
        --------------------------------
        |                              |
   retriever                     answer_chain
        |                              |
 List[Document]                 formatted answer
        |                              |
     sources                       answer
        --------------------------------
                     |
                 combined result


So the final output is:

{
  "answer": "Generated answer text",
  "sources": [Document, Document, ...]
}


📌 Both branches start from the same input (question)

-------

Output parsing: 

in code we see this: StrOutputParser()

what it does ?

Extracts clean text

Removes provider-specific wrappers

Ensures consistent output format


Final RAG chain output:
{
  "answer": string,
  "sources": List[Document]
}



**** str output need:

Why is this needed?

Most chat models (like GPT, Gemini, etc.) return a structured object, not a raw string.

Without StrOutputParser(), you might get:
AIMessage(
  content="The answer is ...",
  metadata={...},
  tool_calls=None
)

With StrOutputParser(), you get:
"The answer is ..."
